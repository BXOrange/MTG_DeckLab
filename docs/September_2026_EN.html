Origin: "Can I Test My Deck in a Sandbox?"

Magic: The Gathering is a game with over 30 years of rules, edge cases, and mechanics that don't fit in a human head. With over 30,000 different cards, there are infinite combinations.

The original question was simple: How do I test a Commander deck without playing against real opponents? How do I validate that a combo chain actually works the way I understand it?

DeckLab began as an internal sandbox mode — called "goldfish" because you play your deck against a passive opponent who takes no actions.

Phase 1: Core Infrastructure (July–August 2026)

The first commits show the classic bootstrapping sequence:

  • Frontend Layout & Deck Import – A clean German interface for entering decklist text
  • Card Database – A local SQLite cache with Scryfall integration
  • Deck Storage – Persist saved decks and retrieve them
  • Basic Game Engine – The first gameplay loop attempts

Key Insights:

  • Offline-first: The project should start without internet.
  • Separation of Concerns: Frontend (JavaScript, no build), Backend (Python FastAPI), clear API boundaries.
  • Decklist Parser: Available on both sides to avoid redundancy.

Phase 2: Game Engine Foundation (July–August 2026)

The real challenge began: implementing the Comprehensive Rules.

The MTG rulebook is not just large—it's also tricky:

  • The Mana Pool — hybrid mana, Phyrexian mana, color restrictions (RULE 605)
  • Combat — ~30 evasion keywords, blocking restrictions, complex damage assignment
  • The Stack — a state machine with Priority (RULE 117), trigger limitations, resolution
  • Permanents with State — Tap/Untap, counters, transformation (DFCs), levels

Breakthroughs from this phase:

1. Token Handling

Cards can create tokens during play. These are GameObject instances, not real Cards. The token-database approach became standard.

2. Layer System (RULE 613)

A conceptual turning point. Effects resolve into 7 numbered layers—addition, subtraction, type changes, control transfers—in this exact order, always.

3. Effect Binding

A GameEffect is a typed object: {"type": "deal_damage", "amount": 3, "recipient": "target"}. An AbilitySpec is pure data—the security boundary between oracle text and code.

4. Ability Catalogue

Hand-write abilities for cards instead of parsing them. Later became the fallback for parser gaps.

Phase 3: Parser Foundation (August 2026)

The parser is Magic's biggest problem. Oracle text is half-regulated, half prose. Syntax is not context-free.

The parser was built in phases:

  1. normalize: Unify notation.
  2. segmenter: Break text into sentences and clauses.
  3. catalogue/handlers: Each effect type has a handler.
  4. gate.parse_oracle: The main gate.

Critical Insights:

  • Fail-closed is better than half-baked: Cards are only `MODELED` if every clause is recognized.
  • Pattern matching is hard: Atomic pieces composed beats monolithic grammar.
  • Metrics are critical: Measure coverage after each change.

Phase 4: Complex Card Structures (August 2026)

With a working parser and engine came difficult card types:

  • Double-Faced Cards (DFCs): Two sides, transform mechanics
  • Sagas: Special permanents with lore counters and chapter triggers (RULE 715)
  • Adventures: Spell with two sides
  • Replacement Effects: "If X happens, do Y instead."

Phase 5: Replay/Puzzle Mode & Board Construction (August 2026)

Before tackling multiplayer, came a different question: What if you want to test a specific board state without playing from turn 1?

Replay/Puzzle mode is a completely different session type:

Arbitrary Board Construction

Instead of playing a legal deck from turn 1, construct any board state. Add creatures, artifacts, enchantments. Set life totals, mana pools, counters.

Two-Player Setup

1 player = pure puzzle. 2 players = with an opponent.

Full Edit API

edit_* actions mutate state directly: add/remove/move objects+tokens, tap, flip, counters, life, poison, player counters, turn markers, phase.

Save/Load as JSON

Export a board state as a re-resolvable descriptor. Cards by name/id, tokens self-describing. Import back later to resume.

Same Engine, Different Semantics

Replay uses the exact same GameSession/GameEngine as goldfish, with mode="replay" and require_setup=False.

Why This Matters for Deck Testing: If you're testing whether a specific combo works starting from turn 5, you don't construct the whole board. Export a goldfish position, switch to Replay, modify, and verify.

Phase 5b: Multiplayer & Sessions (August–September 2026)

After goldfish and Replay worked, came the big question: What about real PvP?

Multiplayer is not just "play with more players." It's a completely different category:

Lobby

Players join a table. Not authenticated, but with a client_token for session continuity.

Presence & Reconnects

A 90-second grace period if disconnected. Priority passes automatically.

Priority (RULE 117)

The real challenge. Stack pauses; active player has priority. Interactive and real-time.

WebSockets

Bidirectional board-update broadcasting per player.

Bots

"Solo gegen Bots" (UC5). A real multiplayer table with AI players.

Key Discovery: The engine doesn't need multiplayer logic. It only needs per-action actor IDs and per-view perspective filters.

Phase 6a: Static & Dynamic Deck Analysis (August–September 2026)

Deck analysis has two layers that together answer "Is this deck legal? Does it actually work?"

Static Analysis (immediate, no simulation)

Decklist Parsing

Server-side text parser stripping foil markers, tag/set suffixes, validating structural commands.

Commander Legality

Real legality checking — color identity, ban list, RULE 903.3 legendary eligibility, all partnership families.

Coverage Assessment

Which cards are MODELED vs. UNMODELED. Per-deck cache (keyed on PARSER_VERSION + catalogue fingerprint).

Mana Curve Analysis

Per-color distribution, generic pips, color intensity.

Dynamic Analysis (simulated)

Game Simulation

Run N independent matches (default: 8) with shuffled random seeds, capturing opening hands and first few turns.

Process Pool Parallelization

Each match is CPU-bound, fanning across ProcessPoolExecutor for real speedup (~3x on 10-core box).

Metrics Capture

Opening-hand quality, first-turn land drop rate, turn-to-first-spell, actual mana curve validation. Structured data, not prose.

Key Insight: "My deck has 40% lands, good mana curve" means nothing if it never draws lands when it needs them. Simulated games answer real questions about actual playability.

Phase 6b: Massive Parser Batches & ENG-37 (August–September 2026)

Parallel to multiplayer and analysis engine development, came a silent architecture refactoring: ENG-37 — Fusion Retirement

The problem: The oracle parser had "fusions" — specialized effect combinations. Hundreds of them made code unreadable.

The Insight: Write atomic primitives and compose them with a composition language.

A 6-week refactoring reduced the catalog to seq, if_else, optional, for_each, and bind. No more fusions. Code shrank 50%. Test coverage rose.

Lessons from ENG-37:

  1. Small, testable units beat monolithic solutions.
  2. Composition languages are cheaper than hundreds of classes.
  3. Measure before and after major refactorings.

Phase 7: Commander-Focused Sprint + Analysis Refinement (September 2026)

Focus shifted to Commander legality and real Commander decks.

With four features now available—Goldfish for linear play, Replay for targeted testing and board construction, Multiplayer for interactive games, and Dynamic Analysis for statistical deck evaluation—the testing surface became comprehensive.

Key Discoveries:

  • Replay Mode for Deckbuilding: Testing combo-heavy decks meant exporting a goldfish position, switching to Replay, and tweaking the board to verify edge cases.
  • Complex Mana Lands: Filter lands needed a new auto-tap engine with converter simulation.
  • Hand-Author-Card Skill: For one-card gaps, hand-writing is faster than parsing.
  • Coverage Measurements: Global coverage doesn't matter—deck coverage does.
  • Concurrent Sessions: Shared docs needed isolation via temporary git indices.
  • Half-Implementations Cost: Finish, hand-author, or defer. No pretty halves.

Critical Lessons

1. Metrics Lie

A new parser rule looks like "+20 cards." But what matters: do your decks work? Solution: parser_probe.py AND engine_bench.py.

2. Half-Implementations Are Expensive

A deferred primitive becomes a debt. That debt resurfaces 4 months later, deferred again.

Discipline: Finish it, hand-author it, or move it to DEFERRED. No pretty halves.

3. Fail-Closed Is Better Than Half-Working

UNMODELED doesn't work. MODELED is guaranteed correct. Opposite of "mostly working."

4. Decompose, Don't Fuse

5 composition primitives + combinatorics beats 100 specialized classes. Longer, yes. More maintainable, yes.

5. Isolation Is Critical

Multiple sessions = own test cache, own config. MTG_CACHE_DIR env var + temp git index.

6. The Parser Is Unfinished and Always Will Be

30,000 cards = cards with unique syntax. Escape valve (hand-author-card) is cheaper than parsing everything.

Where DeckLab Stands Today

DeckLab is not a commercial service. It's a rules-accurate game engine for yourself, built on the conviction that true rules accuracy matters more than coverage.

TL;DR: From "I want to test a deck" to "I built a full MTG rules engine"—in 2.5 months. Detours (ENG-37), setbacks (parser coverage), surprising insights (fail-closed is gold, half-implementations are expensive). Today: it works. Not perfect, but right.

For the Future

Next focus: the long tail. 15,000 unmodeled cards—but if only 100 are in your decks, coverage is irrelevant.

Tools exist: scripts/commander_tail_report.py, scripts/deck_coverage.py. Strategy: sort by "which cards are in real decks" and start there.
